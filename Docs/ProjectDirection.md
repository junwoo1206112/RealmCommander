# Realm Commander 프로젝트 방향 진단

## 결론

현재 프로젝트의 취업 포트폴리오 방향은 타당하지만, RTS, RPG, AI, 1v1 네트워크, 데이터 도구를 모두 완성품처럼 보이게 하는 범위는 너무 넓다. 가장 설득력 있는 방향은 **서버 권한형 RTS 전투 수직 슬라이스**를 먼저 완성하고, RPG 시스템은 이를 보조하는 영웅 1기와 스킬 2개 수준으로 제한하는 것이다.

## 권장 핵심 루프

1. 로비에서 Host 또는 Client로 접속한다.
2. 각 플레이어가 자신의 유닛만 선택하고 이동시킨다.
3. 서버가 이동, 공격, 자원 소모, 승패를 검증한다.
4. 본부 파괴 시 결과 화면을 표시하고 로비로 돌아간다.

이 루프는 2026년 6월 11일 두 개의 독립 Windows Player 프로세스에서 LAN 및 오버레이 IP로 자동 검증되었다. 따라서 유닛 소유권과 이동 동기화 범위의 `Mirror 1v1`은 완료 기능으로 표기할 수 있다. 공인 WAN/NAT 통과와 본부 파괴 후 로비 복귀는 별도 완료 조건으로 남는다.

## 현재 강점

- `RTS`, `RPG`, `Network`, `UI`, `Editor` 폴더로 관심사가 구분되어 있다.
- Mirror의 `Command`, `ClientRpc`, `SyncVar`를 사용한 서버 권한 구조의 기초가 있다.
- CSV 스펙과 자동 문서화 도구가 있어 데이터 중심 개발 역량을 보여줄 수 있다.
- GDD, Architecture, TestCases 문서가 있어 의도를 설명할 기반이 있다.

## 현재 위험

- 네트워크 프리팹의 `NetworkIdentity`와 소유권 연결이 자동화되지 않으면 실제 1v1 제어가 깨진다.
- 클라이언트가 모든 유닛의 전투 `Update`를 실행하면 중복 공격 요청과 비소유 객체 명령 오류가 발생한다.
- `Application.dataPath` 직접 파일 접근은 Android/iOS 빌드에서 CSV 로딩을 보장하지 않는다.
- 문서의 완료 표기와 실제 자동 테스트, VFX, AudioClip, 저장 기능 사이에 차이가 있다.
- 모든 게임 코드가 기본 `Assembly-CSharp`에 있어 모듈 경계와 테스트 격리가 약하다.

## 단계별 우선순위

### P0: 플레이 가능한 네트워크 수직 슬라이스

- 플레이어별 팀과 유닛 소유권을 서버에서 할당한다.
- 이동과 공격을 서버에서만 시뮬레이션한다.
- 두 인스턴스 Host/Client 로그 검증 완료. 제출용 영상은 추가한다.
- 본부 파괴, 승패 판정, 로비 복귀를 검증한다.

### P1: 데이터와 테스트 신뢰성

- CSV 스펙을 실제 유닛/건물 생성 시 주입한다.
- 핵심 규칙을 순수 C# 서비스로 분리해 EditMode 테스트를 작성한다.
- 수동 테스트 문서에는 실행 날짜, Unity 버전, Host/Client 조건을 기록한다.

### P2: 포트폴리오 완성도

- 대표 전투 장면의 스크린샷과 60~90초 플레이 영상을 추가한다.
- Commander Hero 1기와 `Arc Strike`, `Rally Heal` 두 스킬만 완료 범위로 연결한다.
- Quest와 Inventory는 `Prototype`으로 명시하고 핵심 1v1 완료 기능에서 제외한다.
- 런타임, 에디터, 테스트 어셈블리를 분리한다.

## 완료 기준

README의 기능은 코드 존재 여부가 아니라 다음 기준을 모두 만족할 때 완료로 표시한다.

- 씬 또는 프리팹에 연결되어 있다.
- 에디터 재생에서 사용 가능하다.
- 네트워크 기능은 Host와 Client 양쪽에서 검증되었다.
- 재현 절차와 결과가 문서 또는 자동 테스트로 남아 있다.
